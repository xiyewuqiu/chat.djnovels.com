# 会话内消息搜索（接入方指南）

在单个会话里按关键词找消息。

**客户端调业务层**：`POST /jim/messages/search`（`https://chat.<domain>`）。
业务层会带上不可伪造的用户身份转发给引擎，客户端不需要（也拿不到）引擎的签名密钥。

**服务端工具可以直连引擎**：`POST /apigateway/hismsgs/search`（回环 `127.0.0.1:65101`），
需要自己算签名，见第 8 节。

---

## 1. 客户端请求（业务层）

```
POST /jim/messages/search
Content-Type: application/json
appkey: <租户 app_key>
Authorization: <用户 token>
```

```json
{
  "target_id": "g1",
  "channel_type": 2,
  "sub_channel": "",
  "keyword": "书单",
  "limit": 20
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `target_id` | 是 | 单聊是对方 user_id，群聊是 group_id |
| `channel_type` | 是 | `1` 单聊 / `2` 群聊。其他值直接拒绝 |
| `sub_channel` | 否 | 子频道，不传为空 |
| `keyword` | 是 | **2–32 个字符**（按字符算，不是按字节：一个汉字算 1） |
| `limit` | 否 | 命中条数上限，缺省 20，上限 50 |
| `from_time` | 否 | 搜索窗口起点（Unix 毫秒）。缺省为最近 7 天 |
| `to_time` | 否 | 搜索窗口终点。缺省为当前时间，**不允许晚于当前时间** |

**没有 `user_id` 字段**，这是刻意的：发起搜索的人从 `Authorization` token 解析，
客户端不能自称是别人。想看"别人能搜到什么"只能拿别人的 token。

> `from_time` / `to_time` 是 2026-11-22 新增的。想缩小范围（比如"只看今天"）就传这两个；
> 不传等价于"最近 7 天"。

---

## 2. 响应

```json
{
  "code": 0,
  "data": {
    "hits": [
      {
        "msg_id": "m_1001",
        "sender_id": "u2",
        "msg_time": 1762900000000,
        "msg_type": "jg:text",
        "snippet": "…这周的书单我看过了，第三本…"
      }
    ],
    "count": 1,
    "scanned": 604,
    "truncated": false,
    "candidate_limit": 2500,
    "window_from": 1762295200000,
    "window_to": 1762900000000
  }
}
```

- `snippet` 是**片段**，不是全文。前后被截断时会带 `…`。
- `scanned` 是这次实际扫了多少条消息，`candidate_limit` 是本次请求的扫描上限（2500）。
- **`truncated`**：`false` 表示时间窗内已经扫完；`true` 表示还有更早的没扫。
- `window_from` / `window_to` 是服务端实际采用的窗口（客户端传的值可能被钳制）。
- 结果是**按时间倒序**的（最近的在前）。

---

## 3. 能力边界（必须知道）

| 边界 | 说明 |
| --- | --- |
| **时间窗内最多扫 2500 条** | 缺省扫最近 7 天；一次请求最多翻 5 页 × 500 条。吃满上限时 `truncated=true`，说明还有更早的没扫 |
| **只搜文本消息** | `jg:text`。图片、文件、语音、合并转发不参与匹配 |
| **只搜一个会话** | 没有"全局搜索"。跨会话搜索需要客户端逐个会话调 |
| **受保留期约束** | 超出租户保留期（默认 7 天）的消息搜不到，与历史消息查询口径一致 |
| **受可见性约束** | 群聊里：非成员搜不到；群配置"新成员看不到入群前消息"时，入群前的也搜不到 |
| **限频** | 同一 `(appkey, user_id)` 每分钟 20 次，超出返回 `17019`（业务层直连引擎时是 `10012`） |

> **`truncated` 是本接口最重要的一个字段**：`true` 表示"时间窗内还有更早的消息没扫到"，
> 客户端应该提示用户可以缩小时间窗再搜，而不是告诉用户"没有更多了"。
>
> 想彻底摆脱 2500 条上限，需要给消息建内容索引（生成列 + 全文索引），
> 那是改变存储结构的工程，目前没做。

---

## 4. 错误码（业务层，客户端看到的就是这些）

| 码 | HTTP | 含义 | 客户端该做什么 |
| --- | --- | --- | --- |
| `0` | 200 | 成功（包括"没有结果"） | 展示空状态 |
| `17003` | 400 | 参数非法（缺 target_id / channel_type 越界 / 关键词长度不符） | 修参数，别重试 |
| `17005` | 401 | 未登录或 token 无效 | 重新登录 |
| `17019` | 200 | 触发限流 | **退避 60 秒后重试**，不要立刻重试 |
| `17000` | 500 | 引擎侧失败（超时、群成员校验失败等） | 提示"稍后再试"，同时上报 |

注意 `17019` 的 HTTP 状态码是 **200**（与业务层其他限流口径一致），
判断要靠 body 里的 `code`，不要只看 HTTP 状态。

"没有结果"永远返回 `code: 0` 加空 `hits`，不用错误码表达——空结果是正常业务状态。

> 业务层把引擎错误码收敛到了自己的码表，**不直接透传数字**：两张表不同源，
> 同一个数在两边含义可能不一样。所以客户端只需要认上面这张表。
> 引擎侧的原始码（12004 / 10012 等）只会在直连引擎时出现，见第 8 节。

---

## 5. 关键词为什么会搜不到

按可能性排序：

1. **消息在扫描范围之外**。看响应里的 `truncated`：`true` 就是这个原因——
   时间窗内还有更早的消息没被扫到。让用户缩小时间窗再搜。
2. **不是文本消息**。图片消息的正文是 URL，不参与匹配。
3. **超出保留期**。默认 7 天，超出后读路径直接不返回。
4. **消息被撤回或删除**。
5. **关键词里带空格**。首尾空白会被去掉，但中间的空白会原样参与匹配。

---

## 6. 客户端接入建议

- **入口位置**：会话详情页的"搜索"按钮，只搜当前会话。不要做成全局搜索，
  服务端没有这个能力，硬做会变成客户端逐个会话发请求、把限流打满。
- **结果点击**：用 `msg_id` + `msg_time` 定位原消息并高亮，不要依赖 `snippet` 拼正文。
- **空结果文案**：`truncated=false` 时说"没有找到相关消息"；`truncated=true` 时应说
  "更早的消息没有搜索到，可以缩小时间范围试试"——不要让用户以为全部历史都搜过了。
  服务端能力边界见第 3 节。
  用户搜不到时最想知道的就是"为什么搜不到"。
- **退避**：收到 `17019` 后至少等 60 秒再重试。
- **不要试图自己填 `user_id`**：接口没有这个字段，发了也会被忽略。搜索范围由 token 决定。

---

## 7. 已知未验证项

- 该接口**没有在真实服务 + 真实 MySQL 上跑过**完整链路（业务层 → 引擎 → 库）。
  引擎侧已在本地 MariaDB + 真引擎上验过：604 条时 `scanned=604/truncated=false`，
  3604 条时 `scanned=2500/truncated=true`。业务层转发链路只有单测。
- 真实 MySQL 8 的排序/collation 语义与本机 MariaDB 不同，边界行为可能略有差异。
- 扫满 2500 条的耗时**没有精确压测**。本机 3604 条规模下主观上是秒内返回，
  但大群、消息体更大（合并转发、长文本）时需实测。
- 业务层到引擎的转发链路（签名、超时、错误码收敛）有单测，但**没有端到端跑过**。

---

## 8. 服务端直连引擎（运维/自动化用）

引擎接口只监听回环，且要自己算签名。规则见
`chatapi/services/apigateway/apis/signature.go`：

```
signature = hex(sha1(app_secret + nonce + timestamp))
```

请求头需要 `appkey`、`nonce`、`timestamp`、`signature` 四个。

```bash
NOW=$(date +%s%3N)
NONCE=$(openssl rand -hex 8)
SIG=$(printf '%s' "${APP_SECRET}${NONCE}${NOW}" | sha1sum | awk '{print $1}')

curl -s -X POST http://127.0.0.1:65101/apigateway/hismsgs/search \
  -H 'Content-Type: application/json' \
  -H "appkey: $APPKEY" -H "nonce: $NONCE" -H "timestamp: $NOW" -H "signature: $SIG" \
  -d '{"user_id":"u1","target_id":"g1","channel_type":2,"keyword":"书单","limit":20}'
```

直连时 `user_id` 由**调用方自己填**，引擎不做身份校验（它信任"能签出签名的人"）。
所以这条路只该给运维和平台后台用，**不要给客户端**。

引擎侧错误码：`12004` 参数非法、`10007` 请求体非法、`10012` 限流（HTTP 429）、
`13006` 不是群成员、`10004` 缺签名、`10006` 签名不匹配。
