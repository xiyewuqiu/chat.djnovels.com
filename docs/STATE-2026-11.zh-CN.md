## 1. 这是什么

两个 Go 仓库 + 一个 MySQL，部署在同一台机器上：

| 仓库 | 角色 | 规模 | 部署 |
| --- | --- | --- | --- |
| `chatapi.djnovels.com` | IM 引擎（JuggleIM fork），单进程启动 19 个服务 | 661 文件 / 8.2 万行 | 65101 API · 65102 nav · 65103 WS · 65109 管理台 |
| `chat.djnovels.com` | 业务层（JuggleChat fork）：登录、好友、群、举报、租户 | 205 文件 / 2.1 万行 | 65110 HTTP · 65111 回调 |

两者共用 `im_db`，客户端同时连两边。完整部署流程见 [`ops/README.md`](../ops/README.md)。

**这不是上游原版**：引擎相对 `v1.8.16` 有 46 个本地独有文件 + 42 个内容不同文件，
业务层有大量业务改造。跟版策略与影响面见 `ops/README.md` 第 11 节、`ops/tools/upstream_diff.py`。

## 3. 真机验证抓到并修掉的三个 bug

这三条是"跑起来"才发现的，看代码看不出来：

1. **API 路径的 webhook 从未生效**。`bases.GetAppKeyFromCtx(ginCtx)` 永远返回空串
   （gin 的 `Value` 只认 string key，`CtxKey` 是自定义类型），导致 `PreSendCheck` 拿到空 appKey、
   查不到租户、直接放行。已修 15 处。见 `docs/feature-audit-2026-11.zh-CN.md` §4.21。
2. **`apiGateway.ipWhitelist` 只存在于文档**。配置项与实现都没有，运维以为有防护。已补。
3. **搜索翻页游标方向错误**。DAO 会把倒序结果重排成升序，取 `page[len-1]` 当游标等于原地踏步，
   表现为 `scanned` 虚高但命中不增加。已修，并加了 msg_id 去重与游标停滞检测兜底。

## 5. 已知边界（不要当成缺陷，是明确取舍）

| 项 | 现状 | 为什么 |
| --- | --- | --- |
| 搜索单次最多扫 2500 条 | 用 `next_to_time` 翻页可覆盖整个保留期 | 不建内容索引的代价：用扫描量换存储结构稳定 |
| 限流是进程内实现 | 单 PM2 进程成立，多进程会各算各的 | 换 Redis 才有意义，当前没有多实例 |
| 登录方式取决于部署 | SDK 不假设密码登录一定可用 | 账号体系由接入方自己掌控（这正是"大一统"的前提） |
| 真实 MySQL 8 未验证 | 本地用 MariaDB + `utf8mb4_unicode_ci` | 官方 zip 下载 403，镜像只有 msi；collation 边界行为可能有差异 |
| 内嵌迁移 `sqls/*.sql` | 本地为绕开 collation 被跳过 | 只在生产升级时执行 |
| 长连接只验了握手 | 没验证完整消息收发 | `ops/tools/im_e2e.py` 是现成的端到端脚本，需在服务器上跑 |
